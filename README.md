# 陶瓷窑炉燃气负荷回归

澄浦陶瓷的烧成班组在交班前核对温区和累计燃气表，试算当前窑次的参考用气量，把配方单和节拍调整一起交给工艺主管签核。

## 场景

澄浦陶瓷是虚构的釉面砖工厂，有两台辊道窑和 12 名烧成、工艺与能源岗位人员。班组原先把热电偶 CSV、燃气抄表单和配方版本分别维护在共享盘、纸质表和电子表格中。交班有三个常见问题。

1. 温区导出时间对不上进出窑边界，保温段断档时仍可能拼出一条曲线。
2. 累计表漏抄或跨表号相减会掩盖实际燃气用量。
3. 新配方还在审批时，交班备注容易把用量差写成配方效果，工艺主管也难沿备注查回具体读数。

上游是窑次排程、热电偶导出记录、燃气总表和试配方申请。班组在本台账完成覆盖校验、负荷试算和提报。工艺主管确认新的计划节拍后，下一班在周期复核页查看确认人、配方版本和依据。

| 岗位 | 工号 | 页面与权限 |
|---|---|---|
| 烧成班长 `operator` | `firing` | 登记烧成排程，补录温区和累计表，提交试算，提报配方及节拍方案 |
| 工艺主管 `supervisor` | `chief` | 查阅台账、按原快照重试失败任务、审批配方、确认下一周期节拍 |
| 能源查阅 `viewer` | `energy` | 查阅三个业务页、试算快照和交接轨迹 |

三个演示账号使用密码 `KilnLab!1073`。

## 启动

在项目目录执行。数据库卷首次创建时执行 SQL 初始化脚本，后台启动时装入演示数据。

```sh
cp .env.example .env
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --build --wait
docker compose --env-file .env exec -T backend python -m scripts.seed_demo
```

前端 `http://localhost:18272`，FastAPI 文档 `http://localhost:19272/docs`，PostgreSQL `localhost:17772`。在浏览器中使用前端 `/api/` 代理。开发时可通过 `docker compose logs -f backend worker` 查看运行情况。前端目录挂载后浏览器刷新即可看到改动，修改 Python 后用 `docker compose up -d --build backend worker` 重建。终止演示并清除本项目测试数据时执行 `docker compose down -v --remove-orphans`。

| 服务 | 实现与持久化职责 |
|---|---|
| frontend | Nginx，原生 HTML/CSS/ES modules |
| backend | Python 3.12、FastAPI、Pydantic、JWT 与 PostgreSQL 事务 |
| worker | Python、scikit-learn。Redis 投递试算任务 ID，数据库持久化任务和结果，并在通知丢失后补取 |
| db | PostgreSQL 16，命名卷 `database` |
| redis | Redis 7，AOF 与命名卷 `cache` |

API 和 worker 共享 `artifacts` 挂载。算法输入和结果通过数据库存储和追溯。`.env.example` 提供三个端口、Compose 名称、数据库密码、JWT 密钥和 `SEED_DEMO` 开关。演示账号与示例密钥适用于本地验收。

## 班组演示

1. 06:00，打开 `K2-1121-A`，核对 K2 辊道窑、釉面砖 Y17 V3、装载 1,170 kg、计划 480 分钟。
2. 14:05，提交负荷试算，被 `K2-1121-A-TC.csv` 中缺失的保温阶段拦截。
3. 14:08，班长补登记 09:00–11:00、峰值 1,180 °C 的保温段。再次试算会指出 08:00 到 12:00 的抄表间隔过长。
4. 14:11，从 `K2-1121-A-GAS.csv` 补 10:00 的累计 1,319.147 m³，表号 `GM-K2-08`。进窑 1,250.400 m³，出窑 1,363.100 m³，实测差为 112.700 m³。
5. 14:13，重新校验并提交。成功后冻结曲线和读数，负荷分析页可展开来源表、模型度量和快照摘要。
6. 14:18，提报 Y17 低水分釉料，系统分配 V4。班长提出 465 分钟节拍，选择「关联获批配方」。待审状态阻止提交。
7. 14:25，工艺主管核对留样与配方单后批准 V4。班长重新提交节拍方案，主管确认周期。
8. 15:00，能源岗展开节拍方案关联的试算快照，查看三段曲线、五条累计读数和审批轨迹。

另有一组完整的 `K2-1120-B`、一组尚未采集的 `K1-1121-C`。seed 按账号和批次自然键装入，保留用户补录和签核内容。

## 回归口径

阶段时长取所登记区间端点之差。七项输入为装载量、升温/保温/冷却时长和三个温区峰值。固定种子 1073 生成 160 条合成历史窑次，留出 40 条用于 MAE，其余采用 `StandardScaler` 标准化，再由 5 折 `ElasticNetCV` 搜索 α 与 L1 比例。计算留出集 MAE 后记录预测量、实测量（末读数减首读数）、偏差（实测减参考）、训练数据摘要、输入摘要和标准化系数。试算失败保留原快照，工艺主管可重试。训练指标衡量合成样本上的拟合误差。批准配方后，复核单可关联配方版本和同时观察到的负荷差。节拍数值由岗位人员填写和审批。

## 目录与状态枚举

- `backend/migrations/001_kiln_ledger.sql` 定义档案、事实记录、版本、任务和复核关联。
- `backend/kiln/` 包含请求契约、接口、炉窑台账、配方与周期审批、异步 worker 和算法。
- `backend/scripts/seed_demo.py` 装入班组练习数据。
- `frontend/src/` 包含请求与会话状态、共享组件、烧成、分析和复核页面。
- `Phase` 与 `BatchStatus` 在 `backend/kiln/schemas.py`、`backend/migrations/001_kiln_ledger.sql` 和 `frontend/src/state.js` 定义。角色约束在迁移、`backend/kiln/app.py` / `infra.py` 与 `frontend/src/state.js` 体现。配方审批状态分布在迁移、`schemas.py` 的审批动作、`reviews.py` 和 `state.js`。试算状态见迁移、`ledger.py`、`worker.py` 和 `frontend/src/load.js`。

## 业务核验模块

登录后打开页面右下角的「业务核验」。可从实时业务台账筛选记录、导出所选结果，主管可对当前证据签认并填写说明。

- **燃气表跨度审计** 按烧成批次比较抄表覆盖起止及燃气表数量，定位缺首尾点或跨表需要补证的记录。
- **配方变更证据对照** 关联配方变更、回归结果与签认状态，重点标出有变更需求而尚无有效归因的批次。

### 二次扩展核验

- **窑炉热段交接完整性** 按应有的升温、保温、冷却顺序核对时间边界和来源文件，为班组定位漏段、重叠和间隙。

## 专项业务核对

登录后打开「业务核验」，可以筛选和导出记录，主管可签认指定证据。

- **烧成时长预算分解** 按完整批次拆分升温、保温、冷却和曲线外时间，呈现与计划对比。资料缺段时不将差值认作真实空档。
- **同配方吨耗横向比对** 只用单表、累计读数未倒退且覆盖首尾的样本计算吨耗，与同窑、同配方、同版本的上个有效批次对照。
- **燃气估算复核版本锁定** 并排显示班组已引用的估算、本批最新有效估算和最新获批配方版本，定位有新证据但仍沿用旧估算的复核。
